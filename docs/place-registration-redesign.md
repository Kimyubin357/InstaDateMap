# 장소 등록 과정 UI·UX 재설계 — 미착수

2026-10-27 사용자가 장소 등록 과정 전반의 디자인을 개선 과제로 지정했습니다. 현재는 **원인 조사와 과제 기록만 완료**했으며, 이 문서 작성 과정에서 등록 로직과 화면은 수정하지 않았습니다.

다음 UI 작업은 [AGENTS.md](../AGENTS.md)의 미해결 **가로 모드 설계부터** 진행합니다. 이 과제는 링크 입력 화면 일부의 색·간격만 고치는 작업이 아니라, 최종 저장 전까지의 판단 과정과 실패 후 복구 동선을 함께 설계하는 작업입니다.

## 사용자 피드백과 범위

- 장소 저장 진입, 인스타 주소 입력·직접 검색, 분석 진행, 후보 확인, 지점 선택, 최종 저장 직전 화면의 디자인이 만족스럽지 않음.
- 저장 실패 후 나오는 ‘확인 필요’, 확인 대기 목록과 재시도·직접 검색·제외하기 흐름도 함께 재설계해야 함.
- 사용자가 제공한 딩티엔/용산역 확인 화면을 문제 사례로 사용한다. 기능 버그 조사와 화면 재설계는 별도 작업으로 추적한다.
- 기존 원단·손글씨·잉크색·선 아이콘은 [디자인 철칙](design-principles.md)을 따른다. 중첩된 점선 카드와 큰 여백을 그대로 복제하지 않는다.

## 재현된 문제: 체크한 식당이 저장 대상 0곳이 됨

사례 링크: <https://www.instagram.com/reels/Dex5LUzTYz1/>

첨부 화면에는 캡션에서 읽은 ‘딩티엔 용산점’과 위치 태그에서 읽은 ‘용산역’이 함께 표시됩니다. 용산역에는 지도 지점 후보 3개가 보이지만, 딩티엔을 체크한 화면에는 지도 지점 후보가 없고 ‘여기 없어요, 직접 검색’만 보입니다.

코드를 변경하지 않고, 같은 후보 구조를 독립 로컬 테스트 DB에 넣어 실제 `ConfirmForm`에서 다음을 재현했습니다. 운영 데이터나 실제 카카오 검색 응답을 재현한 것은 아닙니다. 저장 요청은 브라우저에서 가로채 실제 저장하지 않고 내용만 검사했습니다.

1. 초기 상태: 딩티엔 후보 `[]` → 체크 해제, `pickedId=null`. 용산역 후보 존재 → 체크 및 첫 후보 선택. 버튼은 ‘1곳 지도에 저장’.
2. 용산역을 해제하고 딩티엔 체크: 체크박스의 `include`만 `true`가 되고 `pickedId`는 여전히 `null`.
3. 저장 개수는 `include && pickedId`만 세므로 0. 버튼은 ‘아무것도 저장하지 않기’로 바뀜.
4. 저장 요청은 `include && !!place`로 다시 계산하므로 딩티엔도 `include:false`로 전송됨. 실제 서버는 정상 권한·버전인 이 요청을 받으면 저장 0곳으로 링크를 완료 처리할 수 있음.

따라서 **‘이름 추출 성공’, ‘지도 장소 연결 필요’, ‘사용자가 제외함’을 하나의 체크 상태로 표현하는 UI·상태 모델의 문제**입니다. 단순히 버튼 문구만 고치면 실제 저장 요청의 문제는 남습니다.

### 코드 근거

- [`ConfirmForm.tsx`](../src/app/confirm/[sourceId]/ConfirmForm.tsx): 후보 유무에 따른 초기 체크, `pickedId`, 저장 개수 계산, 체크박스 변경, 저장 요청의 `include` 재계산, 0개 버튼 문구.
- [`locationTag.ts`](../src/lib/extract/modules/locationTag.ts): 광역 지역 태그만 제외하고 ‘용산역’ 같은 장소 태그는 독립 후보로 채택. 식당의 보조 위치 정보인지 본문 목적지인지 구분하지 않음.
- [`kakao.ts`](../src/lib/kakao.ts): 지역·이름·지점 조합으로 검색하고 점수 3 미만을 제외해 최대 3개 후보를 반환.
- [`pipeline.ts`](../src/lib/pipeline.ts): 한 장소에라도 지도 후보가 있으면 후보가 없는 추출도 함께 확인 화면으로 전달. 서버 확인은 선택된 지도 장소를 기준으로 처리.
- [`005_reliable_workflows.sql`](../supabase/migrations/005_reliable_workflows.sql)의 `dm_confirm_source`: 포함된 장소만 저장하고 링크를 `done`으로 처리함. 0곳 완료도 허용.

### 아직 확인되지 않은 부분

- 이 릴스 처리 당시 딩티엔의 실제 카카오 검색어·원본 응답·점수별 제외 내역은 확인하지 못함. **검색 결과 자체가 없었는지, 상호/지점 표기 차이 등으로 후보 필터에서 제외됐는지는 미확정**.
- 인스타 원문은 외부 조회에서 가져오지 못했으며, 첨부 화면의 캡션 증거와 코드로 조사함. AI 추출 원본과 당시 운영 DB를 확인했다고 간주하지 않는다.
- 카카오 검색 결과가 없다는 이유만으로 식당이 실제로 없거나 카카오에 등록되지 않았다고 결론 내리지 않는다.

## 후속 설계·수정 과제

- [ ] ‘이름은 찾음 / 지도 장소 확인 필요 / 저장 준비됨 / 사용자가 제외함’을 명확히 구분하고, 다음 행동을 각 장소 가까이에 표시.
- [ ] 체크한 장소에 지도 지점이 없으면 최종 저장을 차단하거나 지점 선택으로 안내. 이 상태를 자동으로 ‘아무것도 저장하지 않기’로 처리하지 않기.
- [ ] 0곳 완료·링크 제외는 사용자가 의도적으로 선택하고 결과를 이해할 수 있는 별도 동선으로 설계.
- [ ] 캡션 목적지와 역·동네 등 위치 태그의 관계, 기본 선택 우선순위를 검토. 지도 후보가 있다는 이유만으로 주변 역을 방문 목적지로 기본 선택하지 않도록 판단 기준 마련.
- [ ] 후보가 없는 장소에 ‘지도에서 찾지 못했어요’와 구체적인 검색/지점 선택 행동 제공. 다른 장소에 후보가 있다고 전체 복구 안내를 숨기지 않기.
- [ ] 후보 카드의 제목·출처·주소·지점 선택 계층 정리. 중첩 카드, 과도한 세로 길이, 비선택 항목의 과한 흐림과 뒤로가기/제외/저장의 시각적 우선순위 개선.
- [ ] 링크 읽기 실패, AI 분석 실패, 지도 매칭 실패, 통신 실패, 다른 기기의 작업, 저장 결과 확인 중을 구분. ‘확인 필요’로 뭉뚱그리지 않고 다음 행동을 제공.
- [ ] 직접 검색·재시도 후 입력과 선택 보존, 중복 저장 방지, 저장 완료·이미 저장됨·전체 제외의 결과 안내를 일관되게 설계.
- [ ] 저장할 장소 수와 아직 확인이 필요한 장소 수가 버튼·본문·실제 요청에서 일치하도록 검증.

## 완료 기준

- 이 사례에서 식당만 체크한 사용자가 지점 미선택 상태를 명확히 이해하고, 식당을 지도에 연결한 뒤 저장할 수 있음.
- 체크한 항목이 설명 없이 요청에서 제외되거나, 미완료 확인이 0곳 완료로 소실되지 않음.
- 정상·후보 없음·일부 후보 없음·복수 지점·전체 제외·네트워크 중단·재시도·동시 편집 사례를 실제 렌더링과 요청 내용으로 검증.
- 320×568, 568×320, 667×375, 844×390, 932×430에서 제목·입력·후보·하단 행동이 겹치거나 잘리지 않음. iPhone PWA의 키보드·뒤로가기·복귀 동작을 별도 확인.
- 디자인 시안을 먼저 검토하고 기능 수정과 UI 적용의 결과를 함께 기록한 뒤 완료 처리.
