# 장소 등록 과정 UI·UX 재설계 — 1차 적용 (2026-11-25)

2026-10-27 사용자가 장소 등록 과정 전반의 디자인을 개선 과제로 지정했습니다. 2026-11-25 승인된 시안(`design-lab/registration/index.html`, 15개 화면)을 iPhone 15 세로(393×852) 기준으로 1차 적용했습니다. 가로 모드는 사용자 결정으로 뒤로 미뤘습니다.

## 진행 기록: 2026-11-25 1차 적용

**바뀐 것**

- 추출: 장소 후보는 **캡션에서만** 읽습니다. `locationTag` 모듈은 코드만 남기고 라우터(`MODULES`)에서 뺐습니다(`enabled:false`). 캡션 없이 위치 태그만 있는 게시물은 `needs_caption`(내용을 못 읽은 링크)으로 처리합니다. 예전에 위치 태그로 만든 후보는 확인 화면·확인 대기 이름·남은 이유에서 숨깁니다(`module = location_tag`).
- `/add`(시안 1·2): '인스타 주소 / 직접 검색' 탭을 없앴습니다. 맨 위에 저장할 방 카드("'방'에 저장해요" + [바꾸기])와 방 고르기 시트(색·아이콘·멤버 수·장소 수, '최근' 꼬리표, 현재 방 체크, 새 방 만들기 → `/folders`), 입력칸 안 [붙여넣기](`navigator.clipboard.readText`, 안 되면 길게 눌러 붙여넣기 안내), 단축어 3단계, 확인 대기 바로가기(`/?panel=pending`)를 둡니다. `/add?url=`은 지금처럼 바로 시작하고, 확인 대기의 [다시 분석]은 `/add?url=…&retry=1`로 재분석합니다.
  - 저장 대상은 지금처럼 **이 기기에서 연 방(서버 세션 `access_sessions.board_id`)**입니다. [바꾸기]는 그 방을 바꾸므로 다음 저장에도 유지됩니다. "마지막에 저장한 방"은 이 기기 `localStorage`(`datemap-last-saved-room`)에 저장 성공 때마다 기록해 '최근' 꼬리표와 카드 설명에만 씁니다(DB 변경 없음). 설정에서 방을 바꾼 뒤에는 카드가 "지금 보고 있는 방"으로 표시됩니다.
- 분석 중(시안 3): 4단계 '게시물 내용 가져오기 / 장소 이름 읽기 / 지도에서 위치 찾기 / 확인하고 방에 담기'와 지금 단계만 보여 줍니다. '지도로 가 있기'·알림은 넣지 않았고, 떠날 때의 안내는 실제 동작만 적었습니다(저장되면 지도에, 남으면 확인 대기에; 중단된 링크는 `dm_recover_sources`가 확인 대기로 돌림).
- 장소 확인(시안 4–8, `src/lib/registration.ts`): 장소마다 상태 하나 — **위치 확인됨**(고른 지점·주소·[바꾸기]) / **지점을 골라 주세요**(후보 여러 곳, 처음엔 미선택) / **지도에서 못 찾았어요**(후보 없음 → [이름으로 찾기]) / **빼 뒀어요**([빼기]·[담기]). 후보가 하나면 처음부터 위치 확인됨입니다.
  - 아래 버튼: 모두 준비되면 "'방'에 N곳 담기", 하나 남으면 "<이름> 위치 찾기"/"<이름> 지점 고르기", 여럿 남으면 "남은 N곳 확인"(첫 남은 장소로 스크롤·포커스)과 "확인이 남은 N곳은 아직 담기지 않아요". 모두 빼면 버튼이 꺼집니다.
  - 저장 요청은 화면과 같은 `rowState`로 만듭니다(`selectionsToSend`): 준비된 곳만 `include:true`, 뺀 곳은 `include:false`, 남은 곳이 있으면 요청을 만들지 않습니다. **딩티엔 사례의 include/pickedId 불일치가 사라졌습니다.**
  - '아무것도 저장하지 않기' 버튼을 없앴습니다. 0곳 완료는 "저장할 곳이 없나요? 이 링크 정리하기" → 확인창(시안 14, 담지 않을 이름 나열, 기본은 [계속 확인하기]) → 기존 session dismiss로만 합니다.
  - 이름으로 찾기 시트(시안 5): 장소 하나만 바꾸고, 읽은 이름(+이름에 없는 지역)으로 미리 검색하며 다른 검색어 칩, "찾는 곳이 없어요 · 이 장소 빼기"를 둡니다. 지점 고르기 시트(시안 8): 번호·지점 이름·주소와 [여기 없어요]→이름으로 찾기. **작은 지도(후보 번호 핀)는 넣지 않았습니다**(MapCanvas 재사용 비용이 커서 보류).
  - 이름을 하나도 못 읽은 링크(행 0개)는 원인 안내와 [다시 분석]·[이름으로 찾기](기존 직접 저장 `ManualPlaceSearch`)를 둡니다.
  - 확인 화면의 방은 읽기 전용 줄("'방'에 담아요")입니다. 분석이 시작된 링크는 그 방(`sources.board_id`)에 묶여 있어 확인 화면에서 방을 바꿀 수 없습니다. 잘못 담았으면 저장 뒤 '다른 방에 담기'로 고칩니다.
- 서버 가드: `POST /api/sources/[id]/confirm`은 `direct` 없이 `include`가 하나도 없으면 `400 NOTHING_TO_SAVE`(한국어 안내)로 거절하고 링크를 그대로 둡니다. `confirmSelections`에도 같은 검사를 넣었습니다. SQL 마이그레이션은 없습니다. 응답에 `place_ids`(이 링크로 내가 담은 장소 전부)를 더했습니다(기존 필드는 그대로).
- `/add` 실패(시안 10–12, `addFailure`): `needs_caption` → 게시물을 열 수 없어요(비공개·삭제 **가능성**으로 표현, [다른 링크 넣기]·[다시 읽어 보기]·[이 링크 정리]) / `gemini_rate_limit·unavailable` → AI가 잠시 못 읽음([다시 시도]) / 그 밖의 `gemini_*` → AI 분석 한도([이름으로 직접 찾기]=확인 화면) / 링크 아님 / 작업 중(busy) / 그 밖의 오류. `needs_review`(지도에서 하나도 못 찾음·이름 없음)는 실패 화면 대신 확인 화면으로 갑니다(`reviewDestination`). 연결이 끊기면 '저장됐는지 확인하고 있어요'(기존 `VerifiedWrite`·`verifySharedLink`)를 보이고, 확인되지 않으면 [지금 다시 확인]만 둡니다(같은 링크를 두 번 저장하지 않음). 화면 문구에 'Gemini' 같은 서비스 이름을 쓰지 않습니다.
- 확인 대기(시안 13): 왼쪽에 이름(없으면 `reel/…` 링크 끝)·보낸 사람·'오늘 14:02'·방 이름·붉은 이유 한 줄, 오른쪽에 알약 버튼과 그 아래 조용한 글자 버튼을 한 묶음으로 세로 가운데에 둡니다(각 44px). 이유는 저장된 정보만 씁니다: `needs_caption`, `recovery_reason`(AI 잠시/한도/사용 불가, 중단), 후보 수(지도 후보 없는 곳 `missing_count`, 여러 지점 `choose_count` — `/api/places`의 `pending`에 추가). '저장할 곳 없음'·'이 링크 정리'는 모두 확인창을 거칩니다.
- 저장 뒤(시안 9): 지도로 돌아오면 칩(공통 토스트) "'방'에 N곳을 담았어요"와 '방금 담은 N곳' 시트(장소 행 → 상세, [다른 방에 담기] = 기존 `FolderTransferDialog`, [원본 보기])를 띄웁니다. 정보는 `sessionStorage`(`datemap-just-saved`, 5분·같은 방만, 한 번만)로 넘깁니다. 내 위치·전체 보기·+·하단 탭은 그대로이고, 도구 열과 칩만 시트 위 12px로 올립니다. 시트가 열린 동안은 장소 카드를 띄우지 않습니다.
- 용어: 이번에 손댄 화면과 '다른 방에 담기' 시트·장소 상세 버튼 문구를 '방'으로 바꿨습니다. 쓰지 않게 된 `FolderChooser`·`LinkRecovery`·`InlineManualSearch`를 지웠습니다.

## 사용자 피드백과 범위

- 장소 저장 진입, 인스타 주소 입력·직접 검색, 분석 진행, 후보 확인, 지점 선택, 최종 저장 직전 화면의 디자인이 만족스럽지 않음.
- 저장 실패 후 나오는 ‘확인 필요’, 확인 대기 목록과 재시도·직접 검색·제외하기 흐름도 함께 재설계해야 함.
- 사용자가 제공한 딩티엔/용산역 확인 화면을 문제 사례로 사용한다. 기능 버그 조사와 화면 재설계는 별도 작업으로 추적한다.
- 기존 원단·손글씨·잉크색·선 아이콘은 [디자인 철칙](design-principles.md)을 따른다. 중첩된 점선 카드와 큰 여백을 그대로 복제하지 않는다.

## 재현된 문제: 체크한 식당이 저장 대상 0곳이 됨

사례 링크: <https://www.instagram.com/reels/Dex5LUzTYz1/>

첨부 화면에는 캡션에서 읽은 ‘딩티엔 용산점’과 위치 태그에서 읽은 ‘용산역’이 함께 표시됩니다. 용산역에는 지도 지점 후보 3개가 보이지만, 딩티엔을 체크한 화면에는 지도 지점 후보가 없고 ‘여기 없어요, 직접 검색’만 보입니다.

코드를 변경하지 않고, 같은 후보 구조를 독립 로컬 테스트 DB에 넣어 실제 `ConfirmForm`에서 다음을 재현했습니다. 운영 데이터나 실제 카카오 검색 응답을 재현한 것은 아닙니다. 저장 요청은 브라우저에서 가로채 실제 저장하지 않고 내용만 검사했습니다.

1. 초기 상태: 딩티엔 후보 `[]` → 체크 해제, `pickedId=null`. 용산역 후보 존재 → 체크 및 첫 후보 선택. 버튼은 ‘1곳 지도에 저장’.
2. 용산역을 해제하고 딩티엔 체크: 체크박스의 `include`만 `true`가 되고 `pickedId`는 여전히 `null`.
3. 저장 개수는 `include && pickedId`만 세므로 0. 버튼은 ‘아무것도 저장하지 않기’로 바뀜.
4. 저장 요청은 `include && !!place`로 다시 계산하므로 딩티엔도 `include:false`로 전송됨. 실제 서버는 정상 권한·버전인 이 요청을 받으면 저장 0곳으로 링크를 완료 처리할 수 있음.

따라서 **‘이름 추출 성공’, ‘지도 장소 연결 필요’, ‘사용자가 제외함’을 하나의 체크 상태로 표현하는 UI·상태 모델의 문제**입니다. 단순히 버튼 문구만 고치면 실제 저장 요청의 문제는 남습니다.

### 코드 근거

- [`ConfirmForm.tsx`](../src/app/confirm/[sourceId]/ConfirmForm.tsx): 후보 유무에 따른 초기 체크, `pickedId`, 저장 개수 계산, 체크박스 변경, 저장 요청의 `include` 재계산, 0개 버튼 문구.
- [`locationTag.ts`](../src/lib/extract/modules/locationTag.ts): 광역 지역 태그만 제외하고 ‘용산역’ 같은 장소 태그는 독립 후보로 채택. 식당의 보조 위치 정보인지 본문 목적지인지 구분하지 않음.
- [`kakao.ts`](../src/lib/kakao.ts): 지역·이름·지점 조합으로 검색하고 점수 3 미만을 제외해 최대 3개 후보를 반환.
- [`pipeline.ts`](../src/lib/pipeline.ts): 한 장소에라도 지도 후보가 있으면 후보가 없는 추출도 함께 확인 화면으로 전달. 서버 확인은 선택된 지도 장소를 기준으로 처리.
- [`005_reliable_workflows.sql`](../supabase/migrations/005_reliable_workflows.sql)의 `dm_confirm_source`: 포함된 장소만 저장하고 링크를 `done`으로 처리함. 0곳 완료도 허용.

### 아직 확인되지 않은 부분

- 이 릴스 처리 당시 딩티엔의 실제 카카오 검색어·원본 응답·점수별 제외 내역은 확인하지 못함. **검색 결과 자체가 없었는지, 상호/지점 표기 차이 등으로 후보 필터에서 제외됐는지는 미확정**.
- 인스타 원문은 외부 조회에서 가져오지 못했으며, 첨부 화면의 캡션 증거와 코드로 조사함. AI 추출 원본과 당시 운영 DB를 확인했다고 간주하지 않는다.
- 카카오 검색 결과가 없다는 이유만으로 식당이 실제로 없거나 카카오에 등록되지 않았다고 결론 내리지 않는다.
