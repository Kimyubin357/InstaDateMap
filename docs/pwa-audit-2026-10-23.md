## 2026-10-24 사용자 결정 및 추가 구현

- **B01은 사용자 요청으로 제외한다.** 아래 초기 감사와 후속 기록의 미완료 표시는 과거 판단이며, 더 이상 예정 작업에 포함하지 않는다. 기존 메모 충돌 안내·앱 내 닫기 확인은 유지한다.
- 설정의 **삭제한 장소**: 지도에서 삭제하면 메모·상태·저장자·원본 연결을 보관하고 복구할 수 있다. 자동 만료는 없다. 영구 삭제는 DB의 장소와 연결된 저장자·원본 연결·알림 기록을 삭제한다. 여러 장소에서 공유될 수 있는 원본 게시물 자체는 유지한다. 기능 적용 전에 영구 삭제했던 기록을 되살리는 기능은 아니다.
- 삭제한 장소의 재등록은 설정에서 먼저 복구하도록 안내한다. 복구는 새 장소 알림을 만들지 않는다. 오래된 삭제 목록으로 이미 복구되거나 다시 삭제된 장소를 영구 삭제할 수 없다.
- **Gemini 한도 오류 안내**: 실제 API 거부 응답을 근거로 무료 일일 한도, 일일 한도, 일시적 요청 제한, 종류 미확인 한도를 구분해 결과·확인 대기함·확인 화면에 표시한다. 일부 후보가 있으면 자동 저장하지 않고 후보와 이유를 보존한다. API 키·프로젝트 등 원문 오류는 사용자에게 노출하지 않는다. 남은 무료 횟수를 사전에 조회하거나 전체 분석 시간을 제한하는 기능은 포함하지 않는다.
- R06 제외, R08–R12 보류 결정은 유지한다. 이번 Gemini 오류 안내를 R10 전체 시간 제한 구현으로 간주하지 않는다.

## 1. 종합 판단

데이트맵은 **장소를 발견하고 → 함께 보관하고 → 지도에서 다시 찾는 기본 흐름이 갖춰진 상태**다. PIN 입장, 링크 분석, 직접 검색, 지도·리스트, 카드 탐색, 장소 메모, 기기 캐시, 실시간 동기화, 상대방 알림까지 연결되어 있다. 패브릭 테마와 캐릭터도 일관성이 있다.

다음 단계에서는 기능 수보다 **기록이 사라지지 않는지, 저장 결과를 믿을 수 있는지, 실패한 작업에서 스스로 복구할 수 있는지**를 우선 개선하는 편이 좋다. 특히 다음 항목부터 다룰 필요가 있다.

1. 사용 중인 Next.js의 지원 종료와 보안 권고를 확인하고 지원되는 안정 버전으로 이전한다.
2. 뒤로가기에서 작성 중인 메모가 사라지는 문제와, 삭제된 장소의 수정을 성공으로 안내하는 문제를 수정한다.
3. 여러 장소를 한 번에 저장하다 일부만 저장되는 경우를 정확히 처리한다.
4. 통합 검색의 조건부 결과 누락, 지도 로드 실패, 중단된 링크 분석의 복구를 보완한다.
5. 이후 백업, 삭제 복구, 잘못 고른 지점 변경, 알림 진단을 추가한다.

화면 전체를 다시 디자인할 필요는 크지 않다. 현재 분위기와 탐색 구조를 유지하면서 검색 결과의 우선순위, 실패 화면, 작은 화면의 터치·읽기 편의성을 다듬는 방향을 권한다.

## 4. 확인한 기능 문제

### B01 · 제외 · 브라우저 뒤로가기로 메모 초안이 사라짐

**화면 재현:** 장소 상세에서 메모를 수정하고 저장하지 않은 상태로 브라우저 뒤로가기를 실행하면, 메모 폐기 확인 없이 상세가 닫혔다. 확인 다이얼로그도 입력 필드도 남지 않았다.

**원인:** 상세의 내부 닫기·“지도에서 보기”는 `requestLeave`로 초안을 확인한다. 하지만 지도 화면의 `popstate` 처리는 바로 선택 장소와 오버레이를 바꾼다. [PlaceSheet.tsx:41](/C:/Users/USER/Desktop/datemap/src/components/PlaceSheet.tsx:41), [MapApp.tsx:53](/C:/Users/USER/Desktop/datemap/src/app/MapApp.tsx:53)

**개선:** 이탈 확인을 상세의 버튼에만 두지 말고 브라우저 뒤로가기·탭 이동·외부 갱신으로 상세가 사라지는 경로까지 통일한다. 초안 임시 보존과 “저장하고 나가기”도 검토한다. 초안 보관 시 보드·인증 범위를 유지하고 잠금 시 정리한다.

**완료 기준:** 내용이 바뀐 경우에만 확인하고, “계속 작성”은 입력·스크롤을 유지한다. 저장 성공 후 이탈, 폐기 후 이탈, iPhone 뒤로가기 제스처를 각각 검사한다.

### B02 · P1 · 이미 삭제된 장소 수정도 성공으로 응답

**코드 확인:** PATCH는 DB 오류만 확인하고 실제로 수정된 행이 있는지 검사하지 않는다. 상대방이 삭제한 장소를 오래된 화면에서 수정하면 0행 수정이어도 성공으로 안내할 수 있다. [places PATCH:22](/C:/Users/USER/Desktop/datemap/src/app/api/places/[id]/route.ts:22)

**개선:** 수정 결과 행 또는 영향받은 행 수를 확인하고, 없으면 “이미 삭제된 장소예요”와 목록 갱신으로 연결한다. 메모를 저장했다는 잘못된 성공 토스트를 표시하지 않는다.

**완료 기준:** 두 기기에서 A 삭제 → B 메모·상태 수정 시 성공 오인이 없다. 없는 장소의 DELETE를 성공으로 다루는 현재 동작은 안전한 재시도를 위한 것으로 유지한다.

### B03 · P1 · 여러 장소 확인 저장 중 일부만 저장될 수 있음

**코드 확인:** 확인 저장은 장소별 저장을 반복한 뒤 링크를 완료 처리한다. 두 번째 저장에서 실패하면 첫 번째 장소는 이미 저장되었지만 요청 전체는 실패한다. 개별 장소의 트랜잭션은 정상이며, **여러 장소를 묶은 작업의 결과 일관성**이 부족하다. [pipeline.ts:273](/C:/Users/USER/Desktop/datemap/src/lib/pipeline.ts:273)

**개선:** 선택 목록을 한 트랜잭션으로 처리하거나, 일부 성공을 허용할 경우 “2곳 저장 / 1곳 다시 확인”처럼 결과를 구분해 반환한다. 재시도 시 이미 성공한 장소·저장자·알림을 중복 생성하지 않아야 한다.

**완료 기준:** 3곳 중 두 번째 실패를 주입하고 DB·화면 안내·원본 연결·푸시 기록이 같은 결과를 표현하는지 검사한다.

### B04 · P2 · 통합 검색에서 이미 저장된 장소가 양쪽 결과에서 빠지는 조건

**코드 확인·함수 검증:** 저장된 곳은 이름·주소·메모의 문자열 검색으로 찾는다. 새 장소 결과에서는 저장된 카카오 ID를 전부 제외한다. 카카오가 업종 등 추가 정보로 찾은 장소가 로컬 문자열 검색에는 걸리지 않으면, 그 장소가 양쪽 모두에서 빠진다.

예: 이름이 “식당 A”인 저장 장소를 “한식”으로 검색했을 때 카카오는 찾지만 로컬 이름·주소·메모에는 “한식”이 없는 경우다. 합성 입력에서 `카카오 일치 1 / 저장 결과 0 / 새 결과 0`을 확인했다. [place-search.ts:6](/C:/Users/USER/Desktop/datemap/src/lib/place-search.ts:6)

**개선:** 로컬 검색 결과에 “카카오 결과 중 이미 저장된 ID”를 합쳐 저장된 곳으로 보여준다. 이후 새 결과에서 중복을 제외한다. 일반적인 중복 제거 자체가 고장 난 것은 아니며, 기존 테스트의 의도도 이 요구에 맞게 보완해야 한다.

**완료 기준:** 업종·별칭으로 찾은 저장 장소는 “저장됨”으로 한 번 보이고, 새 저장을 유도하지 않는다.

### B05 · P2 · 메인 지도 최초 로딩 실패 후 자체 복구가 없음

**코드 확인·실패 화면 확인:** SDK 로딩은 API 키에 의존한 초기 효과에서 실행된다. 처음 실패하면 오류 문구는 있지만 메인 지도에서 다시 시도할 수 없고, 탭 왕복·연결 복구만으로 초기 로딩을 재실행하지 않는다. 상세 미니맵처럼 새 인스턴스가 생기면 재시도될 수는 있다. [MapCanvas.tsx:108](/C:/Users/USER/Desktop/datemap/src/components/MapCanvas.tsx:108)

**개선:** “지도 다시 불러오기”와 “리스트로 보기”를 실제 동작으로 제공하고, 네트워크 복귀 시 제한적으로 재시도한다. 이미 정상인 지도는 재생성하지 않는다.

**관련 UI:** 작은 상세 미니맵에서는 실패 안내가 미리보기 영역에 잘리고 “지도에서 보기”와 겹치는 것을 320×568에서 확인했다. 좁은 미니맵에는 짧은 오류 문구·재시도만 표시하는 별도 실패 화면이 필요하다.

**완료 기준:** 첫 SDK 요청 실패 → 재시도 성공, 오프라인 → 온라인 복귀, 상세 미니맵의 작은 화면 안내를 확인한다. 이번 환경에서 SDK가 실패한 원인이 운영 앱의 키 설정 오류라고 확인된 것은 아니다.

### B06 · P2 · 링크 확인 화면의 수동 검색에서 이전 결과가 덮어쓸 수 있음

**코드 확인:** 확인 화면 내부 `ManualSearch`는 검색 버튼을 비활성화하지만 Enter 입력은 진행 중에도 새 요청을 보낸다. 요청 순서 확인이 없어 느린 이전 요청이 새 결과를 덮을 수 있다. 통합 검색의 `PlaceSearch`에는 이미 순서 방어가 있어 이 문제와 구분해야 한다. [ConfirmForm.tsx:218](/C:/Users/USER/Desktop/datemap/src/app/confirm/[sourceId]/ConfirmForm.tsx:218)

### 장소 상세·메모·삭제

- 중간 높이로 열리는 시트, 한 단계씩 내려오는 동작, 고정 하단의 카카오맵·복사 버튼, 상태별 색상은 유지한다.
- 상세 지도는 사용자 레퍼런스의 핵심이다. 없애기보다 낮은 화면에서만 높이를 줄여 주소·상태에 더 빨리 접근하게 한다. 지도 실패 안내도 B05처럼 별도로 정리한다.
- 저장하지 않고 나갈 때는 “계속 작성 / 저장하고 나가기 / 버리고 나가기”를 검토한다. 세 동작이 작은 다이얼로그에서 과밀해지지 않게 배치한다.
- 실수 삭제의 피해가 크다. 확인 창만 강화하기보다 짧은 “되돌리기” 또는 휴지통이 더 효과적이다. 프런트 화면만 복구하면 안 되고 메모·저장자·원본 연결까지 복원되어야 한다.
- 잘못된 지점을 고쳤을 때 삭제 후 새로 저장해야 하는 현재 제약을 줄인다. “장소 정보 바꾸기”에서 기존 메모·상태·원본을 유지해 지점만 교체할 수 있게 한다.
- 장소 메모에 최종 수정자·수정 시각이 있으면 상대방의 변경을 이해하기 쉽다. 상시 알림보다 작은 표시와 변경 내역이 적합하다.

## 8. PWA·접근성·성능·유지보수

### PWA와 iPhone

- `viewport-fit=cover`, standalone, 상태바 설정, 안전영역·키보드 대응 코드가 있다. 노치와 하단 빈 공간은 사용자 실기기에서 여러 번 조정한 이력이 있으므로 이번 데스크톱 모의 화면만으로 다시 결함이라고 판단하지 않는다.
- 설치된 iPhone 앱의 키보드, 홈 인디케이터, 상태바 글자, 백그라운드 복귀, 뒤로가기 스와이프는 실기기 필수 항목이다. 작은 Chrome 뷰포트가 이를 대신하지 않는다.
- 서비스 워커는 푸시 표시·클릭용이며 페이지·지도 오프라인 캐시는 제공하지 않는다. “이미 열린 앱의 마지막 목록 유지”와 “통신 없이 앱 새 실행”을 설명에서 구분해야 한다.
- iPhone Web Push의 홈 화면 설치·사용자 동작 기반 권한 요청을 유지한다. iOS에서 허용했다고 해서 서버 등록·실제 표시까지 완료됐다고 판단하지 않는다. [WebKit Web Push 안내](https://webkit.org/blog/13878/)
- Android 우선순위가 올라가면 maskable 아이콘과 앱 바로가기를 검토한다. 현재 PNG 아이콘이 있으므로 “설치 아이콘이 없다”는 지적은 해당하지 않는다.

### 접근성·읽기 편의성

- 박다현체와 패브릭 느낌은 유지하되 주소·긴 메모·숫자의 가독성을 실제 큰 글씨 설정에서 확인한다. 질감은 지금처럼 지도·텍스트에 직접 노이즈를 얹지 않는 방식이 적합하다.
- 일부 보조 버튼은 24~40px 수준이다. 손가락 조작에는 약 44px의 터치 영역을 우선 검토하되 시각 크기까지 모두 키울 필요는 없다. WCAG 2.2 AA의 최소 목표 크기는 24×24 CSS px 또는 간격 등의 예외 조건이므로 작은 버튼을 일괄 규정 위반이라고 단정하지 않는다. [W3C 목표 크기 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- 색상별 상태에는 이미 텍스트가 있다. 방문 띠·선택 상태도 색만으로 구분하지 않도록 접근성 이름을 확인한다. 모든 상태의 대비를 정식 측정한 것은 아니며, 일반 본문 4.5:1 기준의 별도 검사를 권한다. [W3C 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- 시트 핸들은 키보드 방향키 조절을 제공한다. 눈에 보이는 X를 다시 넣지 않고도 VoiceOver에서 닫기 동작을 찾을 수 있는지 검사하고 필요하면 접근성 전용 닫기 동작을 제공한다.
- UI 확대를 제한한 현재 정책은 사용자 요청에 따른 것이다. 대신 큰 글씨·접근성 환경에서 정보가 잘리지 않는지 확인하고, 필요하면 앱 안의 읽기 크기 옵션을 제공한다.
- `prefers-reduced-motion` 환경에서 카드·지도·시트 이동을 줄이는 동작은 유지·검증한다. 정확한 애니메이션 체감은 실제 기기에서 측정한다.

이번에는 실제 사용자 네트워크의 LCP·INP·배터리·지도 프레임 속도를 측정하지 않았다. “현재 성능이 느리다/빠르다”는 단정 대신 측정 과제를 제시한다.

### 코드와 운영 관리

- `MapApp`, `BoardProvider`, 검색·확인 화면에 탐색·상태·네트워크 책임이 모여 있다. 기능 추가 전에 공통 이탈 확인, 공통 요청 제한, 공통 검색 로직을 분리하면 비슷한 버그가 줄어든다.
- `globals.css`와 `fabric-theme.css`는 기능 추가에 따른 덮어쓰기가 누적되어 있다. 디자인 토큰·레이아웃·컴포넌트·테마를 정리하되, 전면 재작성보다 영향 범위별로 진행한다.
- 앱 디자인의 `error`·`not-found` 복구 화면이 부족하다. 오래된 확인 링크·서버 렌더링 오류에도 “다시 시도/지도 열기”가 보이도록 한다.
- 저장소에 지속 실행되는 브라우저 E2E·CI 구성이 보이지 않는다. 현재 단위·API·SQL 테스트에 핵심 모바일 흐름을 추가하고 푸시 전 자동 검사로 연결하는 것이 좋다.
- README와 테마 문서에는 과거 테스트 수·이전 UI 설명이 함께 남아 있다. 예전 “PIN 표시 전환”, “클릭 즉시 상세” 같은 문장을 현재 기능 설명과 구분하고, 현재 가이드·변경 이력·검증 기록을 분리한다.
- 마이그레이션 적용 순서와 배포 확인표는 현재의 `002 → 003 → 004` 기준을 한 곳에서 관리한다. 과거 문서의 일부 단계만 따라도 설정이 끝난 것으로 오해하지 않게 한다.
